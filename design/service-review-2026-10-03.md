## 1. 판단

P2의 계획된 기능 1~5와 제출 안내는 구현·배포되었다. 이전 지적 세 가지도 회귀 테스트와 함께 수정되었다. 다음 단계는 P2를 처음부터 더 구현하는 일이 아니라, 전달 경로의 예외를 보완하고 실제 공고·한글 앱·모바일로 검증하는 일이다.

표준 설정을 공고 원본+정의로 펼쳐 기존 테스트·공개·버전 고정 흐름에 연결한 방식은 일관적이다. 공용 양식과 배우 작업을 계속 분리하고 있어 현재 목적에 맞는다. 장기 프로필이나 AI 자동 수집까지 한 번에 확장할 근거는 아직 없다.

## 4. 남은 결함·개선 후보

아래 코드 검토 결과는 운영에서 장애를 재현한 결과와 구분한다. 우선순위는 제안이며 제품 코드는 이번 작업에서 고치지 않았다.

### R-01. 수정 직후 이전 PDF가 공유될 수 있음 — 우선 수정

2026-10-04 갱신: HWP `File` 객체와 PDF를 연결하도록 수정했다. 같은 작업 ID의 새 HWP가 로딩 중일 때 이전 PDF 공유를 차단하는 회귀 테스트가 통과했다. 운영 배포 전이며 아래는 당시 발견 근거다.

- 근거: [useDelivery.ts](../frontend/src/useDelivery.ts) 25~41행. PDF 상태를 documentId로만 구분한다.
- 조건: 표준 공고에서 PDF 준비 완료 → 같은 작업 ID로 답 수정 → 새 PDF 로딩 중 메일 버튼 클릭.
- 현재 경로: 이전 pdf 상태를 즉시 비우지 않고 ID도 동일하므로 이전 File을 준비된 파일로 본다. 새 답으로 만든 HWP와 다른 PDF를 보낼 수 있다.
- 제안: 생성 결과 객체 또는 생성 revision에 PDF를 연결하고, 새 결과를 받으면 준비 상태를 갱신한다. 느린 PDF 응답·연속 수정·재시도 테스트가 완료 기준이다.
- 증거 수준: 코드 경로 확인. 운영 표준 공고에서 타이밍 재현은 하지 않음.

### R-02. 외부 브라우저 이어받기에서 제출 맥락 유실 — 모바일 검증과 함께

- 근거: [ResumeNotice.tsx](../frontend/src/form/ResumeNotice.tsx), DocumentService.resume.
- 이어받기 주소는 `/apply/{vid}?doc=<작업ID>`이며, 완성 파일은 공고 공개·마감 상태와 별개로 작업 수명 동안 이어 연다. 답 자체는 외부 브라우저로 이동하지 않는다.
- 현재 이어받기는 작업 ID·완성 파일 이름·존재 여부만 복구한다. PDF 우선 설정·submission 없이 완료 화면을 열어 표준 공고도 HWP 우선으로 돌아가고 받는 곳·메일 제목·마감·별도 첨부 안내가 사라진다.
- 답이 이동하지 않아 편집할 수 없는 정책과 별개로 이 제출 맥락 유실은 아직 남아 있다. 입력값을 치환한 메일 제목도 원래 답을 복구하지 않고는 다시 계산할 수 없다.
- 제안: 이어받을 제출 메타데이터와 완성된 메일 제목의 보관 범위를 정한다. 서버 단기 보관 또는 사용자 복사 안내 등 선택지가 있으며, 개인정보/저장 정책 판단 후 구현한다.
- 증거 수준: 코드 확인. 실제 인앱 → Safari/Chrome 전환 미검증.

### R-03. 마감·추가 안내만 있는 제출 안내가 숨겨짐 — 작은 수정 후보

- 근거: [SubmissionGuide.tsx](../frontend/src/form/SubmissionGuide.tsx) 17행의 email·subject만 확인하는 조기 반환.
- 정의 규칙상 네 필드 모두 선택인데, deadline/note만 있으면 화면 전체가 사라진다.
- 제안: 네 필드 중 하나라도 있으면 안내를 표시하고 메일 관련 동작만 조건부로 제공한다.
- 증거 수준: 코드 확인.

### R-04. PDF 실패 시 HWP로 조용히 대체 — 전달 정책을 명시

- 근거: [useDelivery.ts](../frontend/src/useDelivery.ts) 29·36~41행.
- PDF 사전 로딩이 실패해도 ready 상태가 있으므로 completed.file(HWP)을 공유한다. 버튼은 'PDF 메일로 보내기'다.
- 제안: PDF 실패·재시도 상태를 표시하고 HWP 대체 시 형식을 명시한다. R-01과 함께 처리하는 편이 자연스럽다.
- 증거 수준: 코드 확인.

### R-05. 백업 기능과 운영 복구 보장 사이의 차이 — 운영 보완

- 최신 운영 백업의 실제 보유·정기 생성·외부 보관은 미확인이다. 수동 ZIP 기능만으로 자동 보호가 이루어지지 않는다.
- 다운로드 ZIP 크기에는 상한이 없는데 복원 업로드 한도는 20MB다. 데이터 증가 후 다운로드한 백업을 그대로 복원할 수 없는 경우가 생긴다.
- FormBackup.check는 state/version JSON을 읽지만 definition/spec 의미·source.hwp·공개 버전 파일 일관성을 모두 검사하지 않는다. 백업 중 여러 파일을 하나의 변경으로 묶는 잠금 범위도 별도 점검 대상이다.
- 제안: 보관 주기/대상 결정, ZIP 크기 안내 또는 분할·한도 조정, 격리 복원 검증, 공고 버전 단위의 일관성 검사를 순서대로 검토한다.
- 증거 수준: 코드·자동 복원 테스트 확인. 실제 운영 백업 복원은 미수행.

### R-06. 마감·형식·안내의 의미를 더 정확히 표시 — 제품 정책

- 마감은 날짜 문자열 안내이고 자동 종료·시각 검사가 아니다. 운영자가 닫아야 한다.
- 영상 '3개까지'는 안내이며 서버가 개수를 세지 않는다. URL 유효성도 검사하지 않는다.
- '30분 뒤 자동 삭제'는 접근 만료와 주기 정리를 합쳐 단순화한 표현이다. 답 자체는 브라우저 메모리지만 생성 파일에는 개인정보가 들어간다.
- OS 공유는 메일 앱 선택·수신 주소·공고 제목 자동 입력을 보장하지 않는다. 공유 이벤트를 실제 발송 완료로 집계하면 안 된다.
- 제안: 현재 동작에 맞는 문구를 우선 사용하고, 자동 마감·영상 개수 강제·장기 임시저장은 별도 결정으로 다룬다.

### R-07. 실제 문서·모바일·운영 검증 — 출시 품질

- 한글 앱에서 기본/경력 20줄/긴 자기소개/추가 질문/사진 결과를 열어 확인한다.
- 실제 지정 양식 모음 회귀 검사를 다시 연결한다. TableFlow는 표준 양식뿐 아니라 생성 경로에 적용되므로 기존 양식도 확인해야 한다.
- iOS Safari·Android Chrome·카카오/인스타 인앱에서 사진 선택 → 수정 → PDF 공유 → 받는 곳/제목 → 실제 첨부 확인까지 점검한다. 발송은 운영자가 확인 가능한 테스트 수신함으로 별도 승인 후 수행한다.
- TableFlow는 최대 3회 보정이고 실패 시 경고 로그만 남기고 파일 생성은 계속한다. 렌더 성공을 레이아웃 품질 보장으로 취급하지 않는다.
