# 양식 정의(JSON) 작성 규칙 — 에이전트용

이 문서 하나만 읽고 **지원서 파일(있으면) + OTR 공고 이미지·본문**을 함께 확인해, 공고별 **JSON 초안 하나**를 대화에서 써 주기 위한 규칙이다. 지정 지원서가 있으면 양식 정의를, 없으면 예술in 고정 HWP를 사용하는 표준 공고 설정을 돌려준다. Claude Code, Codex, 웹 채팅 등 어떤 AI든 같은 기준으로 쓴다. 서비스에는 AI가 없다. 이미지 읽기/OCR은 팀원이 쓰는 외부 에이전트가 하고, 운영자가 `/admin`에 JSON을 붙여넣어 서버 검증과 테스트 생성을 거쳐 공개한다.

이 문서는 **쓰면서 자라는 규칙집**이다. 운영자(팀원 누구든)가 AI에게 "이 부분 JSON을 이렇게 고쳐줘"라고 다시 요청했다면, 그 고침이 이 문서의 규칙이 모자라서 생긴 것인지 확인하고 문서도 함께 고친다(아래 "고쳐 달라는 요청을 받았을 때"). 실제로 겪은 경우는 "사례집"에, 바뀐 내용은 맨 끝 "변경 기록"에 남긴다.

## 운영자가 주는 것

1. **공고 번호와 자료**: vid, OTR 공고 본문 전체, 공고 이미지 전체(여러 장이면 순서대로), 지정 지원서 파일이 있으면 그 파일. 본문에 링크로 연결된 별도 제출 지침이 있으면 확인한 내용도 함께 준다. 파일이 없다는 것은 지정 지원서가 없다는 뜻이며, DOCX 등 지원하지 않는 첨부를 생략해 표준 지원서로 대체한다는 뜻이 아니다. 링크만 받고 자동 수집하는 흐름은 이번 범위가 아니다.
2. **지정 지원서가 있으면 칸 목록도**: `/admin/forms/<vid>`에 HWP/HWPX 원본을 올린 뒤 `2. 칸 위치 확인` → `칸 목록` 표를 복사한다. 줄마다 `칸 주소 · 행·열(병합) · 원문`이다.
   ```
   칸	행·열 (병합)	원문
   0.0.0	0·0	이름
   0.0.1	0·1	(한글)
   0.0.2	0·2 (1×2)	(영문)
   0.5.3	5·5 (1×2)	cm / kg
   1.0.0	0·0	(빈 칸)
   ```
   - `칸 주소`는 `표.행.칸`(0부터)이다. 출력의 `cell`에 **그대로** 쓴다. `행·열`은 격자 위치라 주소와 다를 수 있다. 주소를 행·열로 계산하지 않는다.
   - 원문이 여러 줄이면 복사본에서 줄이 나뉠 수 있다. 다음 줄에 주소가 없으면 앞 칸 원문의 이어지는 줄이다.
   - 파일을 읽을 수 있어도 칸 주소를 추측하지 않는다. 칸 목록이 없으면 운영자에게 받는다.
3. **지원서 파일이 없으면** 칸 목록도 필요 없다. 공고 본문과 이미지를 읽어 아래 "표준 지원서 공고 설정"을 쓴다. 이미지를 읽을 수 없는 에이전트일 때만 읽지 못한 부분의 글을 운영자에게 요청한다.
4. 공고 자료 없이 기존 양식만으로 작성해 달라는 요청도 처리할 수 있다. 이때는 "양식만 확인, 공고 조건은 미확인"이라고 알리고 수신처·마감 등을 만들어 넣지 않는다. 어느 빈 칸이 사진 자리인지처럼 판단할 수 없는 것은 묻는다. `사진` 표시가 있는 칸이나 사진용임을 확인한 독립된 빈 칸 표를 사진 자리로 본다.

## 공고 자료를 한 번에 JSON으로 옮기는 순서

1. **이미지와 본문을 함께 읽는다.** 에이전트가 이미지 글자를 읽고 본문·첨부의 안내와 대조한다. OCR이 불확실한 이메일 주소, 날짜, 작품·배역명은 추측하지 않고 확인 대상으로 남긴다. 제공한 자료 이후의 공고 수정은 알 수 없다.
2. **요구사항을 나눈다.** 지원서에 쓸 답, 사진 조건, 파일 이름, 제출 파일 형식, 메일 제목, 마감, 별도 첨부·외부 접수 방법을 찾는다. 출연료·시놉시스처럼 지원서 작성에 쓰지 않는 내용을 질문으로 만들지 않는다. "우대"를 자동으로 필수 질문으로 바꾸지 않는다.
3. **기존 형식에 대응시킨다.** 아래 표로 표현할 수 있는 것만 JSON에 쓴다. 근거·미확인 사항·반영 상태는 JSON 밖에 적고, `requirements`·`format`·`pdfFirst` 같은 미지원 키를 만들지 않는다.
4. **지정 지원서가 있으면 구조를 보존한다.** 공고와 양식의 작품·선택지·날짜가 다르면 차이를 알리고 운영자에게 확인한다. 새로운 선택지를 화면에만 더하거나 원본 칸을 말없이 삭제·수정하지 않는다. 칸 목록이 없으면 주소를 만들지 않고 목록을 요청한다.
5. **지원서가 없으면 표준 설정을 쓴다.** 공고에서 요구하는 답을 기본 항목·`extras`·`help`로 옮긴다. HWP/PDF 파일 접수가 가능한 공고가 대상이다. 온라인 폼 전용이나 다른 지정 형식은 표준 지원서로 접수 가능하다고 판단하지 않는다.

| 공고에서 찾은 요구 | 지정 지원서 있음 | 지정 지원서 없음(표준 설정) |
|---|---|---|
| 지원서에 쓸 정보·답 | `items` + 실제 칸에 쓰는 `outputs` | 기본 항목을 재사용하고 부족한 질문만 `extras` |
| 사진 종류·최근 촬영, 경력 기재 범위 | 해당 항목의 `label`·`help`, 필요하면 `required` | 기본 항목의 `help`. 사진 칸 수·기본 필수 여부 변경은 설정으로 불가 |
| 영상·포트폴리오 링크 | 기재 칸이 있으면 입력·출력. 없으면 별도 제출 안내 | `video` 또는 `custom`. 영상 파일 자체를 생성·첨부하지는 않음 |
| 파일 이름 규칙 | `fileName`, 필요한 입력 항목 | `fileName`, 기본 항목 또는 `extras` |
| 메일 제목 규칙 | `submission.subject`, 필요한 입력 항목 | `submission.subject`, 기본 항목 또는 `extras` |
| 받는 이메일 | 명시돼 있으면 `submission.email` | 같음 |
| 마감일·시각 | 확실한 날짜만 `submission.deadline`, 시각 등은 `submission.note` | 같음. 자동 공개 종료가 아님 |
| PDF만 / HWP 제출 / 별도 사진·영상 / 용량·쪽 수 제한 | `submission.note`로 원문 조건 안내, 강제할 수 없는 것은 확인 목록에도 적음 | 같음. 형식 선택·장수·용량·쪽 수 강제 기능이 아님 |

- **파일 이름과 메일 제목은 따로 읽는다.** 제목만 지정했으면 파일 이름 규칙으로 간주하지 않는다. 둘이 같다고 명시했을 때만 같은 템플릿을 쓴다.
- 날짜는 확실한 연·월·일이 있을 때만 `YYYY-MM-DD`로 옮긴다. 연도 불명·본문과 이미지 충돌·불확실한 OCR은 생략하고 확인 사항으로 남긴다. 시각은 버리지 않고 안내에 남긴다.
- `submission.note`는 고정 안내 글이며 `{id}`를 답으로 치환하지 않는다. 최상위 `note`는 운영 메모이고 배우 화면에 나오지 않는다.
- **현재 완료 화면은 `submission.email`·`subject`가 둘 다 비면 제출 안내 전체를 숨긴다.** 날짜·메모만 JSON에 넣어도 배우에게 보이지 않는다. 보이게 하려고 가짜 주소·제목을 넣지 말고 확인 목록에 "설정에 기록, 현재 화면에서는 미표시"라고 적는다.
- 지정 양식에 칸이 없는 추가 질문을 파일 이름 전용 항목으로 위장하지 않는다. 기재 위치 추가는 별도 양식 수정이 필요하다. 파일 이름·메일 제목에서 실제로 쓰는 답만 전용 항목으로 받을 수 있다.
- 표준 설정에서 배역 하나로 고정이면 `roles` 한 개 대신 `drop`의 `role`을 쓴다. 파일 이름·메일 제목에 배역이 필요하면 확정된 배역명을 글자로 쓰고, 삭제한 `{role}`을 참조하지 않는다.

### 팀원이 그대로 쓰는 요청문

```text
design/form-definition-guide.md를 읽고 다음 자료로 공고 JSON을 만들어줘.
공고 번호(vid):
지정 지원서: 첨부 있음 / 없음
OTR 본문: 아래 붙여넣음
OTR 이미지: 전체 첨부
지정 지원서가 있을 때 칸 목록: 아래 붙여넣음(아직 없으면 받는 방법 안내)

지원서가 있으면 원본 기준 정의 JSON, 없으면 standard-v1 설정 JSON 하나를 줘.
이미지도 읽고 추가 질문·사진 조건·파일 이름·제출 형식·메일 제목·마감·별도 첨부를 대조해줘.
기존 지원 키만 쓰고, 미지원 요구나 원본과의 충돌은 JSON 밖의 반영표와 확인 목록에 적어줘.
제출 안내가 부족한 것만으로 지원서 생성 실패라고 판단하지 마.
```

## 에이전트가 돌려줄 것

1. JSON 한 덩어리(코드 블록 하나, 주석 없이 그대로 붙여넣을 수 있게).
2. **요구사항 반영표**: `요구사항 | 근거(본문 문구 / 이미지 번호·위치 / 지원서 칸) | JSON 반영 위치 | 상태`의 짧은 표. 상태는 `반영` / `안내만 가능` / `운영자 확인` / `현재 미지원`으로 구분한다. 이미지 OCR 전문을 전부 나열할 필요는 없다.
3. **운영자가 확인할 판단**: 필수 여부, 선택지 표기, 원본과 공고의 충돌, 파일 이름·제출 형식, 넣지 않은 항목과 이유. 생성 정확도에 영향을 주는 문제와 선택적인 제출 안내의 누락을 구분한다. 알 수 있는 내용은 초안에 채우고 실제로 필요한 확인만 묻는다. 원본 칸 주소가 없거나 핵심 선택지가 충돌하면 공개 가능한 완성본이라고 말하지 않는다.

## 고쳐 달라는 요청을 받았을 때 (이 문서도 같이 고친다)

운영자가 돌려준 JSON의 일부를 고쳐 달라고 하면(예: "경력은 한 칸에 여러 줄로 받아줘", "성별은 괄호에 V 말고 동그라미로") 다음 순서로 한다.

1. **JSON을 고친다.** 고친 JSON 전체를 다시 준다(부분만 주지 않는다).
2. **고침을 분류해 한 줄로 알린다.**

   | 분류 | 뜻 | 문서 |
   |---|---|---|
   | 이 공고만의 판단 | 공고 안내·운영자 취향을 반영한 것. 다른 공고라면 처음 규칙대로 가는 게 맞다 | 고치지 않는다 |
   | **규칙 부족·오류** | 이 문서대로 했더니 틀렸거나, 문서에 없는 모양이라 잘못 골랐다. 다음 공고에서도 같은 실수가 난다 | **고친다** |
   | 서비스 한계 | 정의 형식으로 표현할 수 없다(예: 제출 파일 형식 강제, 칸 일부 글자만 굵게) | "알려진 한계"에 적고, 개발 요청으로 넘긴다 |

3. **규칙 부족·오류면 문서 수정안을 만든다.**
   - 어디를: 해당 절(형식 / 칸을 정의로 옮기는 법 / 돌려주기 전에 확인)의 규칙 문장을 고치거나 더한다. 이미 있는 규칙과 부딪히면 어느 쪽이 맞는지 운영자에게 묻는다. 말없이 바꾸지 않는다.
   - "사례집"에 한 줄 더한다: 칸 원문 모양 → 처음 쓴 것 → 고친 것 → 규칙.
   - "변경 기록"에 한 줄 더한다: 날짜, 무엇을 바꿨나, 근거 사례(vid).
   - 저장소를 직접 고칠 수 있는 AI(Claude Code, Codex 등)는 이 파일(`design/form-definition-guide.md`)을 바로 고치고 무엇을 바꿨는지 알린다. 웹 채팅처럼 파일을 못 고치면 **붙여넣을 수 있는 수정안**(어느 절에 무엇을 넣고 무엇을 빼는지)을 따로 준다. 커밋은 운영자가 한다.
4. **규칙은 일반적으로 쓴다.** "22373에서는…"이 아니라 "사진 칸에 안내 글이 있으면…"처럼 칸 모양 기준으로 쓴다. 공고 고유 이름은 사례집에만 둔다.
5. **이 문서와 서버 규칙이 어긋나면 서버가 맞다.** 고친 JSON이 저장 검증에서 거절되면 문서의 형식 설명이 틀린 것이다. 문서를 고치고 변경 기록에 적는다. 서버 쪽 규칙(`backend/src/main/java/kr/yesulin/actor/form/`)을 바꾸는 개발이 생기면 이 문서도 같은 변경에서 고친다.

## JSON 형식

```jsonc
{
  "title": "작품명 배우 지원서",        // 필수. 배우 화면 맨 위 제목
  "fileName": "{nameKo}_지원서",        // 선택. 완성 파일 이름 기본값 템플릿(확장자 제외). 배우가 화면에서 고칠 수 있다
  "note": "운영 메모",                  // 선택. 화면에 나오지 않는다
  "items": [ ... ],                    // 필수. 배우 화면에 보일 입력, 적은 순서대로
  "outputs": [ ... ],                  // 필수. 문서 칸마다 하나
  "submission": { ... }                // 선택. 제출 안내(아래)
}
```

위 여섯 개 외의 키는 오류다.

### items — 배우에게 묻는 것

| 키 | 쓰는 타입 | 뜻 |
|---|---|---|
| `id` | 전부(필수) | 영문으로 시작, 영문·숫자·`_`, 40자 이내. 겹치면 안 된다. 예 `nameKo`, `career1`, `photo1` |
| `label` | 전부(필수) | 화면에 보일 이름 |
| `type` | 전부(필수) | `text`, `phone`, `single`, `multi`, `photo`, `rows` |
| `help` | 전부 | 입력칸 아래 안내(예시, 주의) |
| `required` | 전부 | `true`면 비우면 만들 수 없다. 기본 `false` |
| `multiline` | `text`만 | 여러 줄 입력 |
| `maxLength` | `text`만 | 1~5000. 없으면 한 줄 200, 여러 줄 2000 |
| `options` | `single`·`multi`만(필수) | 2개 이상. `{ "id": "영문", "label": "화면 표기", "output": "문서 표기(선택)" }` |
| `min`, `max` | `multi`만 | 고를 개수. `max` 0 또는 없음 = 제한 없음. `min ≤ max ≤ 선택지 수` |
| `columns` | `rows`만(필수) | 1~8개. `{ "id": "영문", "label": "화면 표기" }`. 배우가 한 줄에 열마다 한 줄 글을 쓴다 |
| `maxRows` | `rows`만 | 배우가 쓸 수 있는 최대 줄 수, 1~50. 없으면 10 |

타입에 맞지 않는 키(예: `text`에 `options`)는 오류다.

문서에 들어가는 값:
- `text`: 입력 그대로. 한 줄 항목은 줄바꿈이 공백이 된다.
- `phone`: 숫자만 모아 `010-1234-5678`, `02-123-4567` 꼴로 정리된다. 0으로 시작하는 9~11자리가 아니면 배우에게 다시 묻는다.
- `single`: 고른 선택지의 `output`, 없으면 `label`.
- `multi`: 고른 선택지 표기들을 출력의 `join`(기본 `", "`)으로 잇는다. `fileName`에서는 `_`로 잇는다.
- `photo`: 글자로 쓸 수 없다. `photo` 출력에만 쓴다.
- `rows`: 줄마다 열 값(한 칸 100자, 줄바꿈은 공백). 빈 줄은 버린다. 글자 템플릿·`fileName`에 쓸 수 없다. `rows` 출력에만 쓴다.

### outputs — 답을 문서 어느 칸에 어떻게

칸마다 하나씩, 아래 다섯 방식 중 **정확히 하나**만 쓴다. 같은 칸에 두 번 쓰면 오류다.

| 방식 | 모양 | 동작 |
|---|---|---|
| `text` | `{ "cell": "0.7.1", "text": "{guardianName} / {guardianPhone}" }` | 칸 글자를 템플릿으로 **바꾼다**. 여러 답을 한 칸에 합칠 수 있다(복합 입력). 칸의 원래 안내 글자도 지워진다 |
| `append` | `{ "cell": "0.0.0", "append": "{nameKo}" }` | 칸의 원래 글(라벨)은 두고 **아래 줄에** 쓴다 |
| `edit` | `{ "cell": "0.6.3", "edit": [ { "find": "YES (   )", "replace": "YES ( V )", "when": "tour=yes" } ] }` | 칸 원문에서 `find`를 찾아 `replace`로 **일부만** 바꾼다 |
| `photo` | `{ "cell": "1.0.0", "photo": "photo1" }` | 사진 항목을 칸 크기에 맞춰 넣는다 |
| `rows` | `{ "cell": "2.1.0", "rows": "career", "columns": ["", "title", "role"], "formRows": 10, "grow": true }` | 줄 표 항목을 `cell`부터 한 줄에 하나씩, 오른쪽으로 칸마다 열 하나씩 쓴다 |

- `{id}`는 그 항목의 답으로 바뀐다. `{`·`}` 사이가 항목 id 모양이 아니면 글자 그대로 남는다.
- `join`은 `text`·`append`에만 쓴다(다중 선택 연결 문자).
- `append`는 원본 라벨 서식을 유지하고 입력 첫 글자부터 보통 굵기로 쓴다(`input-typography.md`). 첫 글자만 굵게 보였던 엔진 오류는 수정했으므로 JSON에서 라벨을 지우거나 `text`로 우회하지 않는다.
- **답이 하나도 없으면 그 칸은 원본 그대로 둔다**(템플릿이 가리키는 항목이 전부 비었을 때). 일부만 있으면 빈 자리는 빈 글자가 된다(`"{height}cm / {weight}kg"`에 키만 있으면 `170cm / kg`).
- `edit`의 각 바꿈:
  - `find`는 칸 원문 글자 **그대로**(공백 개수까지) 복사한다. 원문에 없으면 오류다. 같은 글자가 두 번 있으면 앞의 것만 바뀌므로 구분되게 길게 잡는다.
  - `when`: `"항목=선택지"`면 그 선택지를 골랐을 때, `"항목"`이면 그 항목에 답이 있을 때만 바꾼다.
  - `when`이 없으면 `replace`에 쓴 `{id}` 답이 모두 있을 때만 바꾼다(빈 괄호 채우기용). `{id}`도 `when`도 없으면 항상 바꾼다.
  - 바뀐 것이 하나도 없으면 칸은 원본 그대로다.
- `rows`:
  - `cell`은 첫 빈 줄의 첫 칸 주소다. `columns`는 그 줄의 칸마다 넣을 열 id를 왼쪽부터 적는다. 쓰지 않는 칸(번호 칸 등)은 `""`.
  - `formRows`(필수)는 양식에 있는 빈 줄 수다. 그 줄들의 칸이 모두 칸 목록에 있어야 한다.
  - `grow: true`면 배우가 `formRows`보다 많이 쓸 때 마지막 빈 줄을 복사해 아래에 줄을 끼운다. 같은 표에서 그 아래 칸들은 서버가 알아서 밀어 쓴다(주소는 원본 그대로 적는다). 옆으로 병합된 칸은 새 줄에서도 합쳐진다.
  - `grow`가 없으면 항목의 `maxRows`가 `formRows`보다 클 수 없다.
  - `formRows: 0`은 양식에 줄이 없고 모두 새로 생기는 경우다(`grow` 필수). 줄은 `cell` 바로 위 줄을 복사해 그 아래에 생긴다(표준 지원서의 "더 알리고 싶은 것").

### submission — 제출 안내

공고 본문의 접수 방법을 적는다. 배우의 완료 화면에 "받는 곳 / 메일 제목 / 마감"과 복사 버튼, 받는 사람·제목이 채워진 메일 쓰기가 나온다. 서버는 메일을 보내지 않는다.

```json
"submission": { "email": "audition@example.com", "subject": "작품_{role}_{name}", "deadline": "2026-10-15", "note": "자유곡 영상 링크를 함께 보내주세요" }
```

- `email`: 받는 주소. `subject`: 메일 제목 규칙을 `fileName`처럼 항목 id로(`성함` → `{name}`, `지원배역` → `{role}`). 파일 이름은 사용할 수 없는 `/`를 `_`로 바꾸지만, 메일 제목은 공고에서 지정한 구분자를 유지한다. `deadline`: `2026-10-15` 꼴. `note`: 별도 제출물, 제출 형식, 마감 시각 등 고정 안내. 모두 선택이고, 없는 키는 빼도 된다.
- 메일 제목에만 쓰이는 값(지원 역할 등)도 항목으로 받아야 한다. 메일 제목에 쓰인 항목은 "쓰인 항목"으로 센다.
- 공고에 파일 이름 규칙과 메일 제목 규칙이 같으면 `fileName`과 `subject`를 같게 쓴다.

### 검증이 잡는 것 (이걸 통과하게 쓴다)

- 위 키·타입·개수 규칙, id 형식과 중복, `cell`은 `숫자.숫자.숫자`
- 템플릿·`when`·`photo`가 가리키는 항목과 선택지가 있어야 한다. 사진 항목을 `{photo1}`처럼 글자로 쓰면 오류다.
- **모든 항목은 outputs, fileName, submission.subject 중 어딘가에 쓰여야 한다.**
- 원본에 그 칸 주소가 있어야 하고, `edit`의 `find`가 그 칸 원문에 있어야 한다.
- `submission.email`은 주소 꼴, `deadline`은 `YYYY-MM-DD`, `subject`의 `{id}`는 있는 항목이어야 한다.
- `rows` 출력은 줄 표 항목을 가리키고, `columns`의 id가 그 항목의 열이어야 한다. 양식 줄(`formRows`)의 칸이 원본에 모두 있어야 한다.
- 줄을 끼울 수 있는지는 **테스트 생성**에서 확인된다. 위아래로 병합된 칸이 걸친 줄, 표 안에 표가 있는 양식은 오류가 난다. 그러면 `grow`를 빼고 `maxRows`를 `formRows`로 맞춘다.

## 칸을 정의로 옮기는 법

| 원본 모양 | items | outputs |
|---|---|---|
| 라벨 칸 옆 빈 칸 (`이름 \| (빈 칸)`) | `text`, label은 라벨 | 빈 칸에 `text "{id}"` |
| 값 칸에 안내 글 (`(한글)`, `(핸드폰)`) | `text` / `phone` | 안내를 살려 `text "(한글) {nameKo}"` |
| 라벨이 자기 칸에 자리를 남김 (`성명(한글)`만 든 큰 칸, 옆에 빈 칸 없음) | `text` | `append` |
| 연락처·전화·휴대폰·H.P | `phone` | `text` |
| 성별 칸이 비어 있음 | `single` 남·여 | `text "{gender}"` |
| `남(  ) 여(  )`, `YES (  ) / NO (  )`, `□A □B` | `single` (여럿 고르는 안내면 `multi`) | `edit`: 선택지마다 `find` 원문 → `"( V )"`, `"■"`, `when` |
| 한 칸에 값 여러 개 (`cm / kg`, `이름/전화`) | 값마다 따로 | 한 템플릿 `"{height}cm / {weight}kg"` |
| 원문 속 빈 괄호에 값 (`작품명(     )`) | `text` | `edit` `find "작품명(     )"` → `"작품명( {x} )"`, `when` 없음 |
| 안내만 있는 칸 (`년  월  일`, `0000.00.00`) | `text`, 형식을 `help`로 | `text "{birth}"` |
| 넓은 서술 칸 (지원동기, 자기소개, 특장점) | `text` + `multiline` + `maxLength` 400~1000 | `text` |
| 열 머리가 있는 표 + 빈 줄 N개 (`작품명 \| 역할 \| 기간`, 경력·학력) | `rows` 하나, `columns`는 열 머리마다(번호 열 제외), `maxRows` 20 | `rows`: `cell` 첫 빈 줄 첫 칸, 칸마다 열 id(번호 칸 `""`), `formRows` N, `grow: true` |
| 열 없이 한 칸짜리 빈 줄 N개 (안내에 `작품/역할/공연장/연도`) | `rows` 하나, 열 하나(`{ "id": "line", "label": "경력" }`), 안내는 `help`, `maxRows` 20 | `rows`: `columns ["line"]`, `formRows` N, `grow: true` |
| `사진` 칸, 사진 붙이는 빈 칸들 | `photo1`..`photoN`, 첫 장만 `required`(공고가 더 요구하면 그만큼) | `photo` |
| 사진 크기 칸에 안내 글 (`정면 상반신`, `전신 사진`) | `photo`, 안내를 label에 살림(`정면 상반신 사진`) | `photo` (칸 글자는 사진을 넣을 때 지워진다) |

넣지 않는 칸: 라벨 칸, 표 제목·안내 문단, `ex)` 예시 줄, "공란"·"사무국 기재"·접수번호 칸.

그 밖의 원칙:
- **items 순서** = 지원서를 읽는 순서(위→아래, 왼→오른). 짝(키·몸무게, 이름 한글·영문)은 붙인다.
- **label**은 배우가 알아보게 다듬는다(`인스타아이디` → `인스타 아이디`). 긴 질문은 짧게 하고 원문 안내는 `help`로.
- **선택지**: 화면 `label`은 알기 쉽게, 문서에 다른 글자가 필요하면 `output`(`"label": "곰역 및 다역 (남자)", "output": "곰역"`).
- **required**: 이름, 연락처, 성별, 생년월일, 이메일, 지원서·공고가 "필수"라고 한 것, 첫 사진. 애매하면 `false`로 두고 판단 목록에 적는다.
- **fileName**: 공고의 파일 이름 규칙이 있으면 그 순서로 만들고(`/` 대신 `_`), 확장자는 붙이지 않는다. 메일 제목 규칙만 있으면 `submission.subject`에만 쓴다. 문서에 칸이 없는 값(지원 역할 등)이 파일 이름·메일 제목에 필요하면 **전용 항목**으로 받아 `help`에 용도를 알린다. 원본 파일 이름에 자리 표시가 있으면 그 꼴을 따른다(`그대 내 곁에_이름-.hwp` → `"그대 내 곁에_{nameKo}"`, `tf_(이름)_(성별).hwp` → `"tf_{nameKo}_{gender}"`). 없으면 `"{nameKo}_지원서"`. `fileName`에 `.pdf`를 붙여도 PDF 우선이나 PDF 전용이 되지 않는다.
- **title**: 작품·공고 이름 + `배우 지원서`.
- **쪽 수 제한**("한 장을 넘지 않게")이 있으면 서술 칸 `maxLength`를 300~500으로 낮추고 `help`로 알린다. 이는 쪽 수 보장이 아니므로 긴 입력·경력 줄·사진을 넣은 결과도 확인한다.
- 판단이 서지 않는 칸은 넣지 말고 물어본다.

## 표준 지원서 공고 설정 (지원서 파일이 없는 공고)

지원서 파일이 없는 공고는 예술in 표준 지원서(`standard-form.md`)를 쓴다. 정의 전체를 쓰지 않고 이 공고가 **더하고 빼는 것만** 적는다. 운영자는 `/admin/forms/<vid>`의 **양식 정의 JSON**에 AI가 쓴 표준 설정 JSON을 붙여넣고 **저장하고 확인**을 누른다. 별도 시작 방식 선택이나 항목별 설정 폼은 없다. 저장하면 서버가 그 공고의 지원서 파일과 정의를 만든다(원본 파일을 올리지 않는다). 기존 표준 공고도 같은 JSON 입력란에서 설정을 고친다. 이후 테스트·공개는 같다.

```jsonc
{
  "base": "standard-v1",                 // 필수. 기본 양식
  "title": "작품 배우 지원서",            // 필수. 배우 화면 제목이자 지원서 맨 위 공고 줄
  "fileName": "작품_{role}_{name}",       // 선택. 없으면 "{name}_지원서"
  "roles": ["배역1", "배역2"],            // 선택. 2개 이상이면 배우가 목록에서 고른다. 없으면 글로 받는다
  "pickRoles": 1,                        // 선택. 고를 수 있는 배역 수(기본 1, 0은 제한 없음)
  "drop": ["current"],                   // 선택. 뺄 지원 정보 줄: role(지원 배역), current(현재 출연 작품), unavailable(참여 불가 일정)
  "extras": [ ... ],                     // 선택. 지원 정보 아래에 줄로 붙일 질문, 적은 순서대로
  "help": { "photoMain": "…" },          // 선택. 항목 id별 안내 문구 바꾸기
  "submission": { ... }                  // 선택. 제출 안내(위 submission과 같다)
}
```

**extras에 쓸 수 있는 것**(`backend/src/main/resources/standard/standard-v1.extras.json`):

| 키 | 화면·문서 이름 | 입력 |
|---|---|---|
| `video` | 영상 링크 | 여러 줄 글(설명과 링크를 한 줄에 하나) |
| `age` | 나이 | 글 |
| `sns` | SNS | 글 |
| `auditionDates` | 오디션 가능 날짜 | 여러 개 고르기. **선택지를 적는다**: `{ "use": "auditionDates", "options": ["10월 9일 (금)", "10월 10일 (토)"] }` |
| `tour` | 지방·순회 공연 | 가능/어려움 |
| `driving` | 운전 | 가능/불가 |
| `otherRole` | 다른 배역 수용 | 가능/어려움 |
| `longTerm` | 장기 참여 | 가능/어려움 |
| `agency` | 소속 | 글 |
| `nameEn` | 영문 이름 | 글 |
| `military` | 병역 | 군필/미필/면제/해당 없음 |
| `vocalRange` | 음역대 | 글 |
| `hobby` | 취미 | 글 |
| 직접 적기 | 운영자가 정함 | `{ "custom": { "id": "영문id", "label": "질문", "type": "text·yesno·single·multi", "options": [...] } }` |

- 항목은 `"video"`처럼 키만, 또는 `{ "use": "tour", "required": true }`처럼 필수로 쓴다. 직접 적기도 `"required": true`를 옆에 둘 수 있다.
- 기본 항목 id: `name`, `birth`, `phone`, `email`, `gender`, `area`, `height`, `weight`, `school`, `skill`, `role`, `current`, `unavailable`, `more`(배우가 더하는 항목), `intro`, `career`, `photoMain`, `photo1`, `photo2`. 직접 적기 id는 이것과 겹치면 안 된다.
- `drop`은 `role`·`current`·`unavailable`만 가능하다. 셋을 모두 빼려면 `extras`가 하나 이상 있어야 한다. 공고가 기본 질문을 언급하지 않았다는 이유만으로 기본 인적사항·사진·경력을 제거하지 않는다.
- **기본 항목의 필수 여부·타입·사진 칸 수는 이 설정으로 바꿀 수 없다.** `help`는 안내만 바꾼다. 표준 사진은 대표 1장 필수 + 프로필 2장 선택이다. 공고가 사진 2장 필수 또는 4장 이상을 요구하면 안내와 미지원 확인 사항으로 남기며, 새 `photo` 항목이나 기본 항목과 같은 id의 `custom`을 만들지 않는다.
- `custom`의 `text`는 한 줄 200자다. `custom`에는 `id`, `label`, `type`, `options`, `help`만 쓸 수 있고, `required`는 `custom` 밖에 쓴다. 긴 자기소개는 기본 `intro`를 활용한다. 추가 질문의 `multiline`·`maxLength`를 임의로 넣지 않는다.
- 표준 공고는 PDF를 먼저 보여 주고 메일 공유도 PDF를 사용한다. HWP만 제출하라는 공고여도 설정 JSON으로 이를 바꿀 수 없으므로, 반영표에 한계를 적고 운영자가 전달 흐름을 확인한다.

**공고 본문을 설정으로 옮기는 법**:

| 본문 | 설정 |
|---|---|
| 모집 배역이 여럿 | `roles`에 공고 표기 그대로(성별·멀티 표시 포함). 하나만 고르게 하면 `pickRoles` 생략 |
| 모집 배역이 하나, 앙상블만 | `drop`에 `role` |
| 공연 일정이 정해져 있고 불가 일정을 묻지 않음 | 그대로 둔다(배우가 비워도 된다). 공고가 "전체 일정 가능자"를 요구하면 `custom` yesno로 묻는다 |
| 영상·포트폴리오 링크 | `video` |
| 오디션 날짜 중 고르기 | `auditionDates`와 날짜 선택지 |
| 운전·지방 공연·장기 참여 우대 | `driving`·`tour`·`longTerm` |
| 나이가 파일 이름·메일 제목에 들어감 | `age`를 넣고 `{age}`로 쓴다 |
| 사진 조건(최근 6개월 등), 경력 조건(정식 공연만 등) | `help`의 `photoMain`, `career` |
| 메일 주소, 메일 제목 규칙, 마감일, 함께 낼 영상 파일 | `submission` |
| 출연료·연습 장소·시놉시스 | 넣지 않는다(지원서 내용이 아님) |

예(공고 22381을 본뜬 설정, 서버 저장·테스트 생성 확인. 이메일은 예시 주소):

  "title": "어린이 과학뮤지컬 <꼬마박사 장영실> 배우 지원서",
  "fileName": "꼬마박사장영실_{role}_{name}",

## 알려진 한계

정의 형식으로 지금은 표현할 수 없어 개발이 필요한 것. 이런 요청을 받으면 JSON으로 흉내 내지 말고 여기에 적는다.

- 위아래로 병합된 칸이 걸친 줄, 표 안에 표가 있는 양식은 줄을 늘릴 수 없다(`grow` 없이 원본 줄 수까지만).
- 한 줄 표의 여러 열을 한 칸에 이어 쓰기(`작품 / 역할`을 한 칸에): 열마다 칸이 있어야 한다. 칸이 하나뿐이면 1열로 받는다.
- 칸 안 일부 글자만 서식 바꾸기(굵게·색): 입력 글자는 정해진 서식(`input-typography.md`)으로 들어간다.
- HWP가 아닌 원본(DOCX·DOC·XLSX): 아직 올릴 수 없다(`roadmap-standard-form.md`).
- 제출 파일 형식 선택·강제: 일반 지정 양식은 HWP 우선, 표준 공고는 PDF 우선으로 고정이다. 둘 다 HWP/PDF를 제공하며 JSON에 형식 설정은 없다.
- `submission.deadline`은 날짜 안내이며 마감 시각·자동 종료를 지원하지 않는다. `email`·`subject` 없이 날짜·메모만 있으면 현재 완료 화면에서 안내가 보이지 않는다.
- 표준 설정에서 기본 항목 필수 변경·사진 칸 추가·추가 질문의 긴 서술 입력은 지원하지 않는다. 공고의 사진 장수·용량·쪽 수 조건은 자동 강제하지 않는다.
- 별도 사진·영상 파일의 묶음 생성, 첨부·발송 완료 확인, 온라인 폼 자동 제출은 지원하지 않는다.

- [ ] 모든 `find`가 그 칸 원문에서 공백까지 그대로 복사됐다
- [ ] 모든 item이 outputs, fileName, submission.subject 중 어딘가에 쓰였고, 모든 `{id}`·`when`·`photo`가 있는 항목·선택지를 가리킨다
- [ ] 한 칸에 출력 하나, id 중복 없음, 타입에 맞는 키만 썼다
- [ ] `rows`의 `formRows`가 칸 목록의 빈 줄 수와 같고, `columns` 수가 한 줄의 칸 수를 넘지 않는다
- [ ] 라벨·제목·예시 줄 칸에는 쓰지 않았다
- [ ] JSON이 문법상 맞다(끝 쉼표, 주석 없음)
- [ ] 제공된 공고 이미지·본문을 함께 읽었고, 원본과 충돌·OCR 불확실성은 확인 목록에 적었다
- [ ] 파일 이름과 메일 제목을 구분했고, 파일 이름에는 확장자를 넣지 않았다
- [ ] 명시된 수신처·메일 제목·확실한 마감일을 `submission`에 옮겼다. 빠진 자료는 추측하지 않았다
- [ ] 제출 형식·마감 시각·별도 첨부 요구의 반영 상태를 표시했고, JSON에 기록된 것과 화면에 표시·강제되는 것을 구분했다
- [ ] (표준 지원서 공고) `base`가 `standard-v1`이고, `extras`는 목록에 있는 키나 `custom`만 썼다
- [ ] (표준 지원서 공고) 기본 항목과 추가 항목 id가 겹치지 않고, 삭제한 항목을 파일 이름·메일 제목에서 참조하지 않는다
- [ ] 이번 대화에서 고쳐 달라는 요청을 받았다면, 분류(이 공고만 / 규칙 부족 / 서비스 한계)를 알렸고, 규칙 부족이면 이 문서 수정안(사례집·변경 기록 포함)을 냈다
