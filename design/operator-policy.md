# 운영자(개발자) 정책과 운영 절차

기준: 2026-10-03, 커밋 7c34aa2. 현재 구현·기존 확정 결정과 권장 운영 절차를 구분한다. 인프라 설정이나 새로운 권한 정책을 이 문서로 변경하지 않는다.

## 1. 책임과 권한

| ID | 현재 정책 | 운영자의 책임·제약 |
|---|---|---|
| O-01 | 운영자는 공고별 원본·입력·출력·제출 안내를 결정한다 | OTR 본문뿐 아니라 이미지 공고·첨부·외부 제출 절차까지 사람이 확인 |
| O-02 | 서비스 안에는 AI가 없다 | 외부 AI는 가이드를 보고 JSON 초안을 작성. 필수 여부·선택지·원문과의 일치는 운영자가 확인 |
| O-03 | 관리자 API는 공통 Bearer 토큰으로 보호한다 | 개인 계정·다중 역할·관리자별 감사 이력 없음. 비밀은 화면 캡처·채팅·저장소에 남기지 않음 |
| O-04 | 토큰 미설정 시 관리자 API가 꺼진다 | 관리자 화면이 보이는 것과 관리자 API 사용 가능은 별개 |
| O-05 | 토큰은 브라우저 sessionStorage에 둔다 | 탭의 세션에서 사용. '토큰 지우기'는 브라우저 값을 지우며 서버 토큰 회전이 아님 |
| O-06 | 배우 작업과 공용 양식을 분리한다 | 공고 원본에 배우 답·사진을 덮어쓰지 않음. owner는 공고/버전 구분이고 배우 인증이 아님 |
| O-07 | 커밋·푸시·배포는 요청이 있을 때 한다 | main push와 CI 통과가 자동 배포로 이어지는 현재 운영 연결을 고려 |

근거: [프로젝트 규칙](project-rules.md), [공고 링크 설계](notice-forms.md), AdminTokenFilter, adminApi.

## 2. 어떤 공고를 어떤 양식으로 준비하는가

| 공고 유형 | 현재 처리 | 확인할 것 |
|---|---|---|
| 지정 HWP/HWPX 지원서 있음 | 원본 업로드 + 일반 정의 JSON | 지정 원본·사진 조건·파일 이름·별도 첨부 준수 |
| 지정 파일 없고 자유양식/프로필 파일 접수 가능 | 표준 지원서로 시작 | 표준 HWP/PDF로 제출 가능한지 본문·이미지 확인 |
| DOCX·DOC·XLSX 지정 | 현재 원본 엔진 미지원 | 표준 지원서로 임의 대체 가능하다고 안내하지 않음 |
| 온라인 폼·외부 지원 페이지 전용 | 외부 접수 절차 확인·안내 | 파일 생성만으로 해당 접수를 완료할 수 없음 |
| 이미지 안에 요구사항 있음 | 운영자가 이미지 확인 후 수동 설정 | 현재 조사에서 이미지 요구사항은 충분히 분석되지 않았음 |
| 발표·스태프 모집·반복 공고 | 대상·중복 여부 판단 | 'OTR 전체 게시글'을 '고유 배우 모집 공고'로 취급하지 않음 |

조사 189건 중 지원서 없음 118건(62.4%)은 형식 조사 결과다. 표준 지원서로 실제 접수 가능한 비율이나 제품 커버리지로 확정하지 않는다. HWP 56건/지원서 있음 71건(78.9%)도 호환성 통과율이 아니다.

## 3. 양식 준비·공개 정책

| ID | 정책 | 구현·운영 경계 |
|---|---|---|
| O-08 | vid는 1~12자리 숫자로 입력한다 | 시스템은 OTR 존재 여부를 자동 검증하지 않음. 앞자리 0도 문자열상 별도 식별자이므로 원문 번호 사용 |
| O-09 | 일반 양식은 원본과 정의를 함께 준비한다 | 정의는 items와 outputs 분리. 가이드 준수, 알 수 없는 키·참조·원본 칸 문제 확인 |
| O-10 | 표준 양식은 설정으로 원본과 정의를 만든다 | spec.json 보관. base·제목·배역·삭제 줄·추가 질문·안내·제출 정보 |
| O-11 | 표준에서 제거 가능한 기본 줄은 세 개다 | 지원 배역·현재 출연 작품·참여 불가 일정. 셋을 모두 빼려면 추가 질문이 하나 이상 필요 |
| O-12 | 배역 목록은 2개 이상이다 | 하나 선택/복수 선택 가능. 한 배역 고정이면 배역 질문을 빼고 필요한 고정 문구를 파일 이름·제출 안내 등에 직접 명시 |
| O-13 | 표준 기본 사진은 3장이다 | 대표 필수 + 프로필 2장 선택. 기본 항목의 필수 정책을 화면에서 임의 변경하는 기능은 없음 |
| O-14 | 표준 추가 질문은 카탈로그 또는 직접 입력이다 | 직접 질문은 글·예/아니오·단일/복수 선택. 중복 id 금지. 질문 필수 여부는 운영자가 결정 |
| O-15 | 일반 정의나 원본 업로드로 바꾸면 표준 설정이 사라진다 | spec 존재 여부가 PDF 우선 여부에도 영향을 줌. 표준 공고는 가급적 설정을 편집 |
| O-16 | 공개에는 현재 원본+정의의 테스트 성공이 필요하다 | 지문이 다르면 다시 테스트. 테스트 성공 자체는 한글 앱·사진·최대 입력 검증을 대신하지 않음 |
| O-17 | 공개 버전은 불변이다 | 수정하면 새 초안. 기존 공개 링크는 최신 공개 버전을 계속 제공 |
| O-18 | 공개 종료·재개는 운영자가 한다 | 제출 안내 마감일은 자동 종료 기능이 아님 |
| O-19 | 이전 공개 버전도 열린 화면에서는 생성 가능하다 | 공고 전체가 종료되면 기존 화면의 새 생성도 차단 |
| O-20 | 테스트 생성은 완성 카운터에서 제외한다 | 공개 배우 API로 한 운영 점검은 카운터에 포함될 수 있음 |

정의 수정 요청은 [가이드의 수정 절차](form-definition-guide.md)를 따른다. 공고만의 판단인지, 공통 규칙 부족인지, 엔진 한계인지 구분하고 필요한 가이드·사례·변경 기록을 함께 갱신한다.

## 4. 권장 공개 전 점검

현재 자동 공개 조건 외에 운영자가 수행할 품질 확인 절차다.

1. 공고 원문과 제목·대상·배역·필수 정보·사진·별도 파일·접수 방식·메일 제목을 대조한다.
2. 합성 이름·연락처·그린 사진으로 최소 입력을 생성한다.
3. 해당 공고가 허용하는 최대 경력·추가 항목·긴 텍스트·사진을 넣어 생성한다.
4. 미리보기·PDF·HWP에서 누락·겹침·쪽 수·체크·사진·파일 이름을 확인한다.
5. 줄을 늘렸다가 줄여 다시 만들고 클릭 수정 위치와 이전 답 잔존 여부를 확인한다.
6. 변경된 양식 유형은 한글 앱에서 직접 연다. 엔진 재파싱 성공만으로 호환성을 확정하지 않는다.
7. 공개한 실제 링크를 인증 없는 브라우저에서 확인한다. 기기 저장·메일 첨부는 모바일에서 별도 확인한다.
8. 공개·큰 수정 후 외부에 백업을 보관한다. 주기는 아래 미결정 사항에서 정한다.

## 5. 제출 안내·파일 전달 정책

- submission은 일반 지정 양식과 표준 공고 모두 사용한다. email·subject·deadline·note는 모두 선택이다.
- 받는 주소는 형식 검사, 마감일은 YYYY-MM-DD 모양 검사만 한다. 수신 가능 여부·실제 달력 날짜·마감 시각·시간대는 검증하지 않는다.
- 메일 제목의 {id}는 존재하는 글/선택 항목만 사용한다. rows·사진은 제목에 넣지 않는다.
- 메일 제목에 반드시 들어가야 하는 답은 필수로 지정하거나 고정 문구를 사용한다. 빈 선택 답을 제목 템플릿이 자동 보완하지 않는다.
- PDF 우선은 표준 공고에 적용된다. OS 공유에는 파일만 전달되고 받는 주소·공고 제목 규칙이 자동 적용된다고 보장하지 않는다.
- 실제 발송·수신·접수 여부는 서버에서 알 수 없다. 통계의 send_mail은 공유/메일 흐름 시도이지 발송 성공 증거가 아니다.

## 6. 백업·복원 정책

| ID | 현재 정책 | 한계 |
|---|---|---|
| O-21 | 운영자 화면에서 모든 공고를 ZIP으로 받는다 | 자동 정기 백업·외부 저장·최근 백업 알림은 없음 |
| O-22 | 원본·정의·표준 설정·버전 정보·공개 상태를 보관한다 | 배우 작업·렌더 캐시·토큰·로그·카운터는 제외 |
| O-23 | 복원은 서버에 없는 vid만 추가한다 | 기존 vid의 누락 버전 복구·덮어쓰기·롤백은 하지 않음 |
| O-24 | 업로드 ZIP에는 파일·경로·용량 검사가 있다 | multipart 파일 20MB, 해제 후 개별 25MiB·합계 500MiB·20,000파일 제한 |
| O-25 | state/version JSON 구조는 읽어 검사한다 | definition/spec 전체 검증·원본 HWP 재파싱·공개 버전 파일의 완전성 검사는 현재 복원 단계에 없음 |
| O-26 | 복원 테스트는 격리된 빈 저장소에서 한다 | 운영 서버에서 기존 공고를 지워 시험하지 않음 |

백업 다운로드에는 ZIP 크기 상한이 없어, 향후 20MB를 넘으면 그 파일을 현재 업로드 한도로 복원하지 못할 수 있다. '공고 약 200개'는 보장 한도가 아니다. 원본 크기와 버전 수로 판단한다.

복원 전 ZIP의 구조 오류는 반영 전에 검출하지만, 반영 중 I/O 실패까지 전체 공고 단위로 되돌리는 트랜잭션은 없다. 운영 절차에서는 restored/skipped 결과와 대표 링크의 생성 결과를 확인한다.

## 7. 데이터·인프라 운영 정책

- 공용 원본/정의/설정은 Railway /data/forms에 지속 보관한다. 볼륨 지속성과 별도 백업은 다르다.
- 배우 작업은 생성 후 30분 접근 만료, 5분 주기 정리. 재시작 후 작업 인덱스를 복구하지 않는다.
- 단일 서버 인스턴스가 전제다. 여러 인스턴스로 확장하려면 작업 조회·파일 저장·카운터·요청 제한을 함께 재설계해야 한다.
- rhwp에는 슬롯 대기 60초와 개별 프로세스 60초 제한이 있다. 여러 줄 편집·렌더링을 합친 전체 요청의 60초 보장이 아니다.
- 로그는 작업 UUID를 가리고 입력·사진·사용자 파일 이름을 남기지 않는 원칙이다. 상태·시간·IP 등 운영 로그와 GA4 이벤트는 별도 수명이다.
- 실제 지원자 데이터·토큰·공고 원본은 공개 저장소에 추가하지 않는다. 검증 자료는 합성 양식·가상 입력·그린 사진을 사용한다.
- 기존 공개 양식에 적용되는 엔진 변경은 대표 실제 양식 회귀 검증이 필요하다. 표준 양식 테스트만으로 모든 HWP 호환성을 확정하지 않는다.
