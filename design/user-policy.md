# 사용자(배우) 기능·데이터 정책

기준: 2026-10-03. 현재 구현의 기능 정책을 정리한다. 제품 변경 제안은 [점검 문서](service-review-2026-10-03.md)에 별도로 둔다.

## 1. 사용 목적과 입구

| ID | 정책 | 현재 동작 |
|---|---|---|
| U-01 | 회원가입 없이 파일을 작성한다 | 배우 계정·지원 내역·장기 프로필 저장 기능 없음 |
| U-02 | 공고 링크는 운영자가 준비한 양식으로 작성한다 | /apply/{vid}에서 별도 원본 업로드 없이 항목 입력 |
| U-03 | 공고별 작성 링크로 접속한다 | 루트 주소와 잘못된 경로는 공고 링크 안내만 표시 |
| U-04 | 서비스의 완료는 파일 생성이다 | 생성·공유·다운로드가 공연사 접수 완료를 뜻하지 않음 |
| U-05 | 공고가 종료되면 새 조회·생성을 할 수 없다 | 종료 전 만들어 둔 파일은 작업 보관 시간 안에서 별도로 내려받을 수 있음 |
| U-06 | 작성 중 양식이 바뀌어도 열린 버전을 쓴다 | 운영자가 공고를 종료한 경우에는 해당 버전으로도 생성할 수 없음 |

## 2. 입력과 문서 작성

| ID | 정책 | 제한·예외 |
|---|---|---|
| U-07 | 필수 항목과 선택지는 공고별 정의를 따른다 | 화면 안내와 서버 검사 적용. 표준 v1 필수는 이름·생년월일·연락처·성별·대표 사진 |
| U-08 | 표준 양식 사진은 총 3칸이다 | 대표 사진 필수, 나머지 2장은 선택. 공고의 별도 사진 조건은 안내를 확인 |
| U-09 | 표준 경력은 20줄, 자기 항목은 3개까지 추가한다 | 일반 지정 양식은 운영자가 정한 행 수·줄 확장 가능 여부를 따름 |
| U-10 | 줄 표 한 칸은 100자, 빈 줄은 제외한다 | 줄바꿈은 공백 처리. 전체 줄이 비어 있을 때만 제거 |
| U-11 | 사진은 칸 비율에 맞춰 배치한다 | 자동으로 인물을 잘라내는 기능 아님. 결과에서 방향·여백·누락 확인 |
| U-12 | 사진은 브라우저에서 크기·형식을 정리한다 | HEIC 등은 브라우저가 해독할 수 있어야 함. 실패하면 JPG/PNG 사용 안내 |
| U-13 | 파일 이름을 배우가 수정할 수 있다 | 공고의 제출 규칙을 우선 확인. HWP/PDF에 같은 이름을 사용. 서버 제한 1~100자, 경로 문자·예약 이름 등 금지 |
| U-14 | 미리보기에서 입력 항목을 수정할 수 있다 | 같은 브라우저에 답이 남아 있는 경우. 수정 후 같은 작업의 결과를 교체 |
| U-15 | 긴 내용은 여러 쪽이 될 수 있다 | 2~3쪽 보장 없음. 기존 최대 입력 검증 기록은 4~5쪽 사례도 포함 |
| U-16 | 제출 전 배우가 완성본을 확인한다 | 빈칸·체크·사진·페이지·공고 필수 질문·별도 영상·파일 이름 확인 |

표준 추가 질문의 영상은 링크/설명 입력이다. 영상 파일 업로드·촬영·자동 첨부는 지원하지 않는다. 파일 형식이 DOCX·DOC·XLSX이거나 온라인 폼만 받는 공고는 현재 기능으로 그대로 처리하지 못한다.

## 3. 저장과 수명

| ID | 정책 | 정확한 의미 |
|---|---|---|
| U-17 | 입력 답과 선택한 사진은 작성 중 브라우저 메모리에 둔다 | 새로고침·탭 종료 시 답을 복구하는 저장 기능 없음. 서버 생성 요청에는 필요한 답·사진이 전송됨 |
| U-18 | 생성에 필요한 서버 파일은 임시 보관한다 | 원본 사본·사진·완성 HWP/PDF·미리보기 파일에는 입력 정보가 들어 있음. '아무 정보도 서버에 저장하지 않는다'는 표현은 부정확 |
| U-19 | 작업 생성 후 30분에 접근이 만료된다 | 최초 파일 생성에서 작업을 만든 시점부터 시작. 수정해도 수명 연장 없음 |
| U-20 | 파일 삭제는 만료 처리와 주기 정리로 수행한다 | 5분 주기 정리와 접근 시 만료 검사를 사용. 정확히 30분 되는 순간 모든 파일의 물리 삭제를 보장하지 않음 |
| U-21 | 서버 재시작으로 작업에 접근하지 못할 수 있다 | 작업 인덱스가 메모리라 지속 복구하지 않음. 필요한 파일은 기기에 저장 |
| U-22 | 작업 링크는 본인의 파일 접근 정보다 | 작업 ID만으로 보관 중 파일을 조회할 수 있음. 공고 링크와 달리 개인 작업 링크는 공개 공유하지 않기 |
| U-23 | 내려받은 파일은 사용자 기기에 남는다 | 서버 만료가 기기에 저장한 파일이나 이미 보낸 메일을 삭제하지 않음 |

## 4. PDF·메일·외부 브라우저

| ID | 정책 | 현재 구현의 경계 |
|---|---|---|
| U-24 | 표준 공고는 PDF를 먼저 제공한다 | 완료 화면 PDF 메일·PDF 저장·HWP 저장. 지정 양식은 HWP 우선 |
| U-25 | 메일 발송은 배우의 메일 앱에서 마친다 | 서비스에는 SMTP 발송·발송 내역·수신 확인 기능 없음 |
| U-26 | 공유가 가능하면 OS 공유창에 파일을 전달한다 | 특정 메일 앱·받는 사람·제목 자동 입력을 보장하지 않음. 제출 안내의 복사 기능을 함께 사용 |
| U-27 | 공유가 불가능하면 파일 저장 후 메일 작성창을 연다 | 등록된 받는 주소·치환된 제목을 mailto로 전달. 파일 첨부·최종 발송은 배우가 확인 |
| U-28 | 제출 안내는 운영자가 공고에서 옮긴 정보다 | 마감일 표시는 자동 접수 종료나 접수 가능 보장이 아님. 시각·영상 등 세부 조건은 공고 원문 확인 |
| U-29 | 인앱 브라우저에서는 외부 브라우저 사용을 안내한다 | 기기·앱에 따라 자동 이동 또는 버튼/메뉴 안내. 실제 기기별 성공은 별도 확인 필요 |
| U-30 | 외부 브라우저로는 완성 파일만 이어받는다 | 답은 이동하지 않아 편집 불가. 현재 표준 공고의 PDF 우선·제출 안내도 이어받지 못하는 제한이 있음 |

## 5. 이용 제한·분석

- 기본 서버 제한: 문서 20MB, 사진 12MB/장, 요청 합계 60MB. 해상도·파일 실제 형식도 검사한다.
- 기본 공개 POST 요청 제한: 같은 IP에서 10분 60회. 같은 네트워크 사용자는 제한을 함께 받을 수 있다.
- 서버가 보관하는 작업 기본 한도는 300개다. 가득 차거나 변환에 실패하면 재시도 안내가 나온다.
- 운영 사이트는 GA4 화면·저장·공유 이벤트를 사용한다. 앱 코드는 이름·답·사진·파일 이름·작업 ID를 분석에 보내지 않는 원칙을 둔다.
- 요청 로그에는 상태·시간·IP 등이 남고 작업 UUID는 마스킹한다. 따라서 '모든 이용 흔적을 저장하지 않는다'고 안내하면 안 된다.

## 6. 현재 확인된 개선 필요 사항

정책과 실제 동작 사이의 차이를 숨기지 않기 위해 별도로 기록한다. 자세한 근거와 우선순위는 [점검 문서](service-review-2026-10-03.md)를 따른다.

- 표준 공고를 수정한 직후에는 새 PDF 준비 전에 이전 PDF를 공유할 수 있는 코드 경로가 있다.
- PDF 준비 실패 시 'PDF 메일로 보내기'가 HWP로 대체될 수 있으나 그 사실을 알리는 안내가 없다.
- 받는 주소·제목 없이 마감·별도 첨부 안내만 등록하면 제출 안내 전체가 표시되지 않는다.
- 외부 브라우저 이어받기에서 공고의 제출 안내와 PDF 우선 설정이 유지되지 않는다.
