# 공고 목록 관리

2026-10-04 사용자 요청: 공고 목록을 20개씩 페이징하고 vid·공고 제목으로 검색하며 삭제와 이용량 집계를 추가한다.

## 확정: 서버 페이징과 검색

사용자가 전체 목록을 브라우저에서 나누는 방식 대신 서버 검색·20개 페이징을 선택했다. 기존 파일 저장소와 Spring/React 구조를 유지하며 새 라이브러리나 DB를 도입하지 않는다.

- `GET /api/admin/forms?page=1&query=`: Bearer 운영자 인증 필수. `items`, `page`, `pageSize`, `total`, `totalPages`를 반환한다. 기존 배열 응답 대신 페이지 응답을 사용한다.
- page는 1부터 시작하며 0 이하·숫자가 아닌 값은 400이다. 크기는 20으로 고정한다.
- vid 또는 현재 편집 버전 제목의 부분 일치로 검색한다. 검색어 앞뒤 공백과 영문 대소문자를 무시하며 기존 vid 숫자 내림차순을 유지한다.
- 결과가 없으면 빈 1페이지, 요청 페이지가 결과 범위를 넘으면 마지막 유효 페이지를 반환한다.
- 화면은 검색 제출 때 1페이지로 돌아가고 이전·다음, 결과 수, 로딩·오류·재시도·빈 결과를 표시한다. 이전 요청의 늦은 응답이 새 결과를 덮어쓰지 않는다. 백업 복원 뒤 현재 검색을 다시 조회한다.
- 저장소는 검색·전체 결과 수를 계산하기 위해 서버에서 공고 메타데이터를 조회한다. 응답의 공고 항목은 최대 20개이며 서버 디스크 조회 비용이 20개로 제한된다는 뜻은 아니다.
- 목록 화면 책임은 `frontend/src/admin/FormList.tsx`, API 계약은 기존 adminApi/FormViews, 서버 조회는 기존 FormAdminService에 둔다.

## 확정: 복구 가능한 삭제

사용자가 추천안을 승인했다. `DELETE /api/admin/forms/{vid}`는 원본·정의·버전을 보존하고 삭제 상태만 기록한다. 일반 목록에서 제외하고 공개 조회·새 생성은 404로 막는다. 이미 만든 임시 파일은 기존 30분 수명을 따른다.

- `GET /api/admin/forms?deleted=true`는 삭제된 공고만 같은 검색·페이징 규칙으로 반환한다.
- `POST /api/admin/forms/{vid}/restore`는 삭제 전 공개·종료·초안 상태로 복구한다. 모두 기존 운영자 인증을 요구한다.
- 삭제 전 확인창과 삭제 목록의 복구 버튼을 제공한다. 삭제된 공고는 복구하기 전 편집할 수 없다.
- `state.json`의 `deleted`가 없는 기존 파일은 false로 읽는다. 공고 백업은 이 상태를 포함한다.

## 확정: 익명 브라우저와 최초 파일 집계

계정 없이 실제 사람 수를 식별하지 않는다. 화면은 **이용 브라우저**라고 표시한다. 브라우저의 무작위 ID를 localStorage에 보관하고 서버는 SHA-256 해시만 저장한다. 저장소 차단 시 현재 페이지 동안만 ID를 유지하며 저장소 삭제·기기/브라우저 변경으로 중복될 수 있다.

- 공개 공고에서 HWP 생성이 성공한 브라우저를 공고별로 중복 제거한다. 전체 이용 브라우저는 공고 간에도 중복 제거한다. 열람만 한 방문은 포함하지 않는다.
- 작업별 최초 HWP 1개와 최초 PDF 1개를 합산한다. 같은 작업의 재생성·재다운로드·PDF 재변환과 운영자 테스트는 제외한다. 새 작업은 새 파일로 집계한다.
- `X-Usage-Visitor`가 없거나 잘못된 요청도 파일 수에 포함하되 이용 브라우저에는 포함하지 않는다. 이 작업 수를 별도 안내한다.
- 실패한 생성은 해당 형식의 파일 수에 포함하지 않는다. 성공은 서버의 파일 생성 기준이며 이메일 제출·클라이언트 저장 완료를 의미하지 않는다.
- `GET /api/admin/usage`는 시작 시각과 전체 수치를 반환한다. 목록 항목의 `usage`는 공고별 수치다. 전체 수치에는 삭제된 공고도 포함한다.
- `yesulin.usage-file`의 기본값은 `${yesulin.forms-dir}/usage.json`이다. 해시 집합·공고 번호·숫자·시작 시각만 지속 보관하고 이름·답변·작업 ID는 저장하지 않는다. 단일 서버 인스턴스를 전제로 원자적 파일 교체와 작업별 잠금으로 중복을 막는다.
- 집계는 시작 이후만 제공한다. 기존 최초 완성 카운터로 과거 고유 브라우저·형식별 파일 수를 복원하지 않는다. 임시 작업 인덱스는 재시작 후 복원하지 않는다.
- 공고 ZIP 백업에는 이용량 파일을 포함하지 않는다. 이용량을 보존하려면 해당 파일도 별도로 백업한다.

## 로컬 검증과 범위

2026-10-05 격리된 합성 공고 25개로 확인했다. 운영 배포·실제 공고 삭제는 하지 않았다.

- 백엔드 전체 92개, 프런트 전체 53개 테스트와 양쪽 빌드 확인. 검색·20/5개 페이지·빈 결과·범위 초과·인증·삭제 차단·복구 상태·기존 상태 파일·집계 중복 제거·재시작 보존을 검증한다.
- 실제 rhwp로 합성 HWP와 PDF를 만들고 HWP 재파싱에서 입력 칸을 확인했다. 브라우저 1개·HWP 1개·PDF 1개가 반복 PDF 요청에도 유지됐다. 사람의 메일 제출과 한글 앱·실기기는 확인하지 않았다.
- 실제 HTTP 삭제 204 → 공개 조회 404 → 복구 200 → 공개 조회 200, 화면 복구 버튼과 집계 보존을 확인했다. 네이티브 삭제 확인창은 브라우저 도구가 멈춰 승인·취소 완결을 직접 확인하지 못했으며 컴포넌트 테스트로 검증했다.
- 데스크톱·모바일 화면을 직접 확인하고 두 독립 검토가 통과했다. 모바일 통계 안내의 어절 줄바꿈을 고쳤으며 넓은 표는 표 영역에서 가로 스크롤한다.
- 신규 화면/브라우저 ID 파일 lint는 통과했다. 전체 lint는 기존 코드의 anti-slop 진단으로 실패하여 저장소 전체 품질 게이트가 통과한 상태는 아니다.
